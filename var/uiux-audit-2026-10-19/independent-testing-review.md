## Modal root cause: accepted, with evidence limits

`Frontend/src/app/features/work-items/components.jsx:189–223` renders `.d-modal-backdrop`, `.d-modal`, `.d-modal-body`, plus drawer/expanded classes. `FeatureIssuesPage.jsx:37` has root `.cat-container.feature-issues-page`; `WorkBoardPage.jsx` returns that component without `.work-items` wrapper. `TestingDocumentPage.jsx` uses `.testing-page.testing-document.td-page`; CaseIssueAction mounts the same Modal under that route. MainLayout/App add no `.work-items` ancestor.

The layout selectors require the missing ancestor: `work-items.css:1455–1487`, `work-items-live.css:52–63`; drawer and expansion require `.dashboard-board.work-items` in `styles/work-board.css:156,253`. Whole CSS search found no unscoped `.d-modal` replacement. The CSS imports themselves exist in WorkBoardPage; this is selector ownership/ancestry, not simply missing import.

Root screenshot `monkey-dialog-768.jpg` visibly places form below the Issue list with no overlay dimming or modal frame. JSON: viewport768×1024, dialog870.30px high/536px wide, close at y764.30 and Save at y1583.60. Root report additionally measured static backdrop/dialog. **The supplied JSON does not itself store computed position or a full dialog top/bottom rectangle**, so cite root's additional measurement separately rather than pretending JSON contains it. JSON `issue-expanded-768.json` has pressed “Thu nhỏ ticket” but dialog width536/height1167.30 at768×1024, consistent with missing expanded width100vw/height100dvh styles. It does not by itself compare before/after geometry, although source establishes the unmatched expanded selector.

Do not claim data loss, impossible keyboard operation, or every viewport tested from these artifacts. Important pointer/touch workflow is visibly broken; keyboard can sometimes cause a viewport scroll to an offscreen focused control, so “cannot ever submit” would overstate evidence. Root P1 remains reasonable because an important form/detail no longer operates as its declared modal and save/actions lie far outside normal viewport. Accessible names/aria-modal presence do not rescue absent visual modal geometry; no formal WCAG failure asserted without criterion-specific verification.

Fix acceptance should target component-owned scope/current ancestry, including old existing call sites, drawer expanded state, body scroll lock, close/Tab/Escape/return focus, and long body at320/390/768/1440/low-height/zoom. Avoid broad unrelated `.d-*` global styling. TI-002 pending/dirty behavior shares Modal lifecycle but is a separate logic concern; can be a dependent repair task under modal work, not evidence the CSS creates duplicate writes.

## Navigation: accepted with precise scope

`FeatureIssuesPage.jsx:31` generates only local filter params (page,size,type,status,keyword,featureId) and view/from markers. It omits projectId even if incoming route had it. App.jsx navigate directly uses this destination. AppEntry's workspace wrapper re-adds **workspace=1 only**, so the existing Admin reload fix does not repair missing project identity. ProjectProvider chooses project from query or per-user localStorage (`:29–41`); selectProject updates storage and removes a previous projectId (`:58–63`). MainLayout only has special cross-project reset logic for testing Feature deep routes, not Issue paths.

Safe reproduction: from scoped A list open IssueI → copied Issue URL lacks projectId → select B so stored selection becomesB → reopen/reload copied URL. It can requestI under B and fail, rather than selectA. Within the initial same-project session, open/close can still work because currentProject remainsA; avoid claiming an immediate failure on every open. Filter/page changes (`change`, pagination handlers) remain local until a navigation serializes them, so refresh of list alone loses recent filters; independent symptom of incomplete durable URL ownership. Keep linked project restoration and filter persistence as separate acceptance cases under one route-context task. No cross-project data exposure was established.
