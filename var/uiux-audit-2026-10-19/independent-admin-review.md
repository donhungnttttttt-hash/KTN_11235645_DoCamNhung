## AG-S01 — archive readiness: accepted only with the full retirement chain

`Backend/src/main/java/vn/syp/tms/admin/ProjectLifecycleService.java:35` counts old `DOING/PAUSED` file sessions;40 counts active cycles or drafts with runs;41 counts OPEN retest requests.47 sets `canArchive` only when all blockers are empty, and71 repeats enforcement at archive submission. `AdminProjectLifecycle.jsx:59,92` disables confirmation when readiness is blocked. Its guidance8/10/11 tells users to finish old file work/cycles/retests.

This is not a defect simply because the tables exist or contain open rows. `docs/api/project-lifecycle.md:3,15–19` records the deliberately chosen08/10 policy, including OPEN retests even when a Bug had ended. Preservation of historical rows remains intentional after the19/10 conversion. New C08 speaks about **Feature/file archive**, not an explicit rewritten whole-project readiness policy. Do not silently infer that every old blocker should be deleted or ignored.

The specific source problem is the **absence of a supported way to satisfy the displayed remediation**: `LegacyTestingWrites.java:26` identifies FileWorkController/FileWorkSessionController/FileWorkExecutionController, ExecutionController, CycleDecisionController and RetestController as retired;35–39 rejects their writes with410 after authenticated project access. This includes the retained cancel/close methods in the old services, so finding a Java method named cancel does not establish an available user recovery path. AppRouter43 also retires `/tests/**`. GET history and internal fixture/service methods do not provide an ordinary completion action. Current clarification C07 explicitly says the retired request/run/coverage workflow must not continue blocking authorized new operations; even if whole-project archive policy needs reconciliation, the current UI instructions cannot be followed as written.

**Accepted wording:** “Project archive can require completing retired workflows, with no supported public recovery.” **Rejected wording:** “Retained old data is a bug”, “all archive blockers are obsolete”, “old records are completed”, “remove every legacy check”, or “main archive is impossible” without current project evidence. `ALLOCATED_DEVICES`, active external publication and genuine current unfinished Issue checks remain independently meaningful.

**Root reproduction:** inspect existing project readiness via GET/modal only, record blocker types/counts and current route guidance; close without submission. To prove exclusive causation, an isolated fixture containing an old blocker and otherwise fulfilled readiness is required. A main project with both old and current work proves occurrence of the old gate, not that removing it would alone permit archive.

**Acceptance after a future fix:** retain legacy records/history unchanged; archive readiness explicitly classifies retired historical work under a documented current policy; no instructions point to unavailable controls; a suitable disposable project can archive and reopen without reintroducing run/retest workflow; actual unfinished current Issues/devices/external operations and permissions/version/idempotency checks stay protected. No blanket force-completion migration is implied by this audit.

## AG-S02 — Note conflict: accepted; do not “fix” by blindly overwriting the version

`ProjectNotes.jsx:29` captures the selected Note object in `editor.note`;42 always submits `editor.note.version`. “Tải lại Note” at46 increments only the list revision, whose effect19–25 updates `data`; none of that replaces/compares `editor.note`. Edit buttons61 remain disabled while editor exists. Failed mutate36 retains editor text and the stale original version. `ProjectNotesService.java:34` obtains current Note and calls `SettingsVersion.require`; `SettingsVersion.java:9` returns409 for a mismatch. Thus v3 editor → another client savesv4 →409 → list reload → save still sendsv3.

The server protects against lost updates correctly, and the first failure does not erase text. The defect is the UI's lack of a reviewed recovery path that retains the draft. The list may show latest text beneath the editor, but the user cannot submit against its version without cancel/reopen and manually copying/retyping their draft. `notesApi.get` exists at `services/api/notes.js:11`, so a latest-note read seam is already available.

**Scope correction:** this finding is the **edit** conflict. Do not assert deletion uses the identical stuck-version path: deletion confirmation is rendered from each current list `note` at65–66, so a list refresh creates a fresh closure/version even if `removing.id` remains selected. That separate behavior would need its own review, not copied reasoning from the editor.

**Future acceptance:** in an isolated two-client fixture, conflict preserves draft, “compare latest” fetchesv4 and shows a usable distinction between latest and draft, explicit reviewed retry uses current expectedVersion, and a second concurrent change still yields409. Deleted/permission-revoked Note must explain why retry is unavailable. Do not auto-advance version to force the user's old draft over another person's text. No writes were run here.

## TI-007 request fan-out: confirmed architecture, unmeasured impact

`CaseIssueAction.jsx:13–17` eagerly calls `api.list` on mount for that exact project/Feature/document/row. `TestingDocumentPage.jsx:55` mounts an instance for each visible row. Page-size options51 are20/50/100; source default is20. `featureIssues.js:9` delegates directly to the HTTP client; no shared query cache/batch is present. Each request uses size20 and the list payload, not merely a count. Backend `FeatureIssueService.java:91–92` performs total count plus matching rows per call. Therefore up to100 per-case list reads per100-row page is a valid source deduction; it is **not** proof that every document always makes100 requests or that every case has20 Issue rows.

No request waterfall, latency, transfer size, server resource impact, interaction delay or production performance was measured in this independent pass. Eager loading has a legitimate purpose: the visible badge needs a count that includes open and closed issues. A batched-count response plus lazy details is a reasonable optimization, but it cannot become a confirmed P2 performance defect solely from request count.

Keep this as a separate source risk (P3 candidate or optional optimization pending measurements). Do not merge its performance severity with the keyboard popover root cause in TI-007: portal focus/blur behavior and eager fetch cardinality are separate mechanisms with different fixes and acceptance checks. Root may retain a P2 keyboard finding if browser evidence establishes the interaction problem.

**Evidence to promote severity:** with a known read-only fixture, compare20/100 rows, record actual requests/timing and time until controls become usable under stated local conditions; establish visible delayed/error behavior. Do not extrapolate a local result to production. **Optimization acceptance if later adopted:** badges retain exact row/Feature scope and all-status counts, refresh after issue changes, requests are batched/cached/lazy as designed, and keyboard preview doesn't become dependent on a hidden hover-only request. There is no need to invent a universal arbitrary request budget.
